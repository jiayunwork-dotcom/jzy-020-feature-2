给燃烧实验室加一件反过来问的能力：不再只是给定当量比去算火焰温度，而是给一个想要的绝热火焰温度，让服务把能达到这个温度的当量比找出来。台架上常见的诉求是「我要把这个燃烧室稳在某个火焰温度上，进气和燃料定了，配比该调到多少」，现在得靠人拿着正向求解器手动试凑，来回交几十单才逼近，这一层要由服务自己做完。

新增的求解仍然只经 HTTP 提供，落成作业、可用编号取回，和现有正向衡算共用同一套燃料目录、同一套空气组成、同一套热力学系数与温度迭代内核。反解就是在正向求解外面再套一层：内层照旧把某个当量比迭代成火焰温度，外层调节当量比去逼近目标温度。禁止另起一套热力学，也禁止把反解写成查表或多项式拟合，它必须真的反复调用正向衡算。

难点在于火焰温度对当量比不是单调的。固定燃料、固定进气温度，把当量比从很贫扫到很富，火焰温度先随配比变浓而升，在化学计量附近到达一个峰值，再往富里走又因为过量燃料吸热而降下来。也就是说同一个目标温度，只要它低于这个峰值，通常对应两个当量比：一个在贫侧、一个在富侧；恰好等于峰值时只有一个；高于峰值则根本达不到。这条曲线的峰值位置和峰值高度取决于燃料和进气温度，服务得自己把峰值先定出来，再在峰值两侧各自求配比，而不能假定单调、拿一个二分了事。

反解作业的入参是燃料、进气温度、目标火焰温度，以及要找贫侧解、富侧解还是两个都要。约束沿用正向那套：燃料必须在目录内，进气温度必须为正的热力学温度，目标温度必须为正且为有限数；这些在启动外层求解前就要拒掉，带类型的错误。目标温度虽然是正数但高于该燃料该进气下的可达峰值时，作业以「目标不可达」失败，并要把估出来的峰值温度和对应当量比写进结果，让调用方知道最高能到哪，而不是笼统报一句失败或硬凑一个配比。

找到的每一个当量比都要经得起正向复核：把它代回正向衡算，解出来的火焰温度和目标温度之差必须落进钉死的温度容差里；解出来的当量比必须为正；元素仍要闭合，原子残差低于阈值。外层求配比的过程也要像正向那样留痕：每一步的当量比试探值和对应的温度偏差按顺序记下来，写进作业，用编号取回时能看到配比是怎么一步步收敛到目标的，而不是只给一个最终数字。贫侧解与富侧解要分别各自累积各自的收敛序列，不许混进同一条里。达到最大步数仍没把温度偏差压进容差，这一侧就失败，不得报一个其实没对齐目标的当量比。

反解结果和正向作业一样保存下来：燃料、进气温度、目标温度、请求的侧别、找到的贫侧当量比、富侧当量比（各自附上正向复核出的火焰温度、产物摩尔分数、原子残差）、峰值当量比与峰值温度、每一侧的外层收敛序列、温度容差。用编号取回全文。一次反解作业就是针对一个目标温度的一次求配比，不要提供把多个互不相关的目标温度打成一包批处理的入口。缺项、非有限数、侧别取值非法都返回带类型的错误。

对错看这些闭合，说清楚才算做对。甲烷、进气约 298 K，目标温度取化学计量峰值以下的某个值（比如 2200 K 量级里低于峰值的一档），必须能同时给出一个贫侧当量比（小于 1）和一个富侧当量比（大于 1），两个配比代回正向都落在目标温度的容差内，且两者明显不等。把目标温度一路抬高到逼近峰值，贫侧解与富侧解要互相靠拢并向化学计量附近收拢；目标温度取到高于峰值的值，两侧都判不可达并回报峰值。乙烷在同一进气、同一目标温度下反解出的当量比不得和甲烷被写成同一组数：两种燃料的温度随配比变化的曲线不同，峰值也不同，结果必须能分开。只把进气温度抬高再反解同一个目标温度，找到的当量比会随之改变（进气更热意味着达到同一火焰温度只需更贫或更接近化学计量的配比），这个变化方向要成立、要经得起正向复核。服务须内置一条反解示范作业：甲烷、进气约 298 K、给定一个峰值以下的目标温度、请求两侧，贫富两个当量比都解出来且各自正向复核通过。

工程约束跟随现有产物：用 Java 17 与 Spring Boot 经 HTTP 提供，反解作业沿用现有那份随进程启动的 SQLite 落盘，别再拉一个独立数据库进程，打镜像与启动仍是原来那条命令。反解逻辑按职责单独成模块：峰值定位、贫富两侧的外层求根、把当量比代回正向复核、反解作业的存取与入参检查，不要把它塞进已有的正向求解器文件里搅成一团，也不要改动正向衡算既有的对外行为。回归用例至少覆盖：目标温度低于峰值时贫富双解都能正向复核通过且两者不等、目标温度逼近峰值时两侧解互相靠拢、目标温度高于峰值时判不可达并回报峰值、乙烷与甲烷反解结果分得开、抬高进气温度后同一目标温度的解随之改变、非法侧别与非正目标温度在启动外层求解前被拒、内置反解示范作业两侧都收敛、多条反解作业并行时各自的收敛序列互不串扰。
